### CDR-2026-017: Secrets Management (Rule)

Canonical standard signals:
- ESO: `ClusterSecretStore` per backend (shared across namespaces); one `ExternalSecret` referencing it; auth via Workload Identity / IRSA — never static creds.
- DRY: `/<env>/<service>/<secret-name>` path convention; `dataFrom` bulk sync; `creationPolicy: Owner`; refresh interval by sensitivity.
- Security baseline: never commit real secrets; per-environment stores; least-privilege store access; OIDC/Workload-Identity for CI/CD auth.

## Standard-Selection Decision

Q2 resolved: HashiCorp Vault as the single standard. Fleet survey shows the org's actual implementation is ESO+Vault — ESO is the abstraction, Vault is the provider. The canonical standard for this audit = "Vault-backed ESO pattern": repos declare `SecretStore`/`ClusterSecretStore` (Vault provider, Kubernetes auth) + `ExternalSecret` (consistent path convention, `secretKeyRef`/`envFrom` consumption, no committed secrets).

This supersedes the raw Vault alternative (no ESO) and the pure cloud-store ESO pattern (GCP/AWS). Recorded as an explicit standard-selection decision per US2.
